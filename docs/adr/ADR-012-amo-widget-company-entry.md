# ADR-012. Самостоятельный вход администраторов amoCRM

Статус решения принят для ПОДК-01.01. Исполнение тестов и выпуск учитываются отдельно.

Администратор создаёт компанию и входит из настроек любого из трёх виджетов без пароля.
Кнопка находится в модальном окне настроек виджета, доступном администратору amoCRM.
При отсутствии фактической компании она называется «Создать компанию», после создания называется «Перейти в компанию».
Компания определяется для аккаунта amoCRM целиком, поэтому другой наш виджет открывает ту же компанию.
Установка виджета и проверка состояния сами по себе компанию не создают.
Каждый переход выдаёт новую ссылку текущему подтверждённому администратору, а не общую ссылку владельца.
Первый создатель новой компании становится владельцем. Каждый следующий администратор получает собственного пользователя с ролью admin.
Существующая компания без владельца не передаётся тому, кто первым открыл виджет.

TeamOS владеет компанией и привязкой `(rakurs, accountId)` в `company_integrations`.
Core хранит уникальное наблюдение `accountId -> companyId`, проверяет JWT amoCRM и актуальные права конкретного пользователя.
Запись установки, регистрационный токен и продуктовый grant не доказывают существование компании.
Новый read-only endpoint проверяет фактические компании, включая прежнюю `amo_account_id`.
Несколько компаний, несовпадающие привязки и неактивное состояние дают blocked.
Ошибка запроса никогда не означает absent.

`POST /api/v1/provisioning/amocrm/company-status` принимает только `accountId`.
`POST /api/v1/provisioning/amocrm/widget-entries` принимает `accountId`, `actorId`, `integrationId`, `installationId`, `intent`, `name`, `email`.
Оба endpoint требуют `Authorization: Service <GATEWAY_PROVISIONING_SERVICE_TOKEN>` и настроенный provider rakurs.
Новые endpoint требуют credential даже при прежнем разрешении неавторизованного provisioning.
Внутренние RPC дополнительно проверяют отдельный `GATEWAY_COMPANY_SERVICE_TOKEN`.
Браузерные дополнительные поля, включая роль и компанию, отклоняются строгим JSON-декодером.
Core вызывает эти endpoint только после проверки текущего администратора.

`intent=create` создаёт или повторно находит компанию под транзакционной блокировкой аккаунта.
`intent=enter` отказывает, если компании уже нет.
Новая компания, пользователь, external identity, события outbox и handoff сохраняются одной транзакцией PostgreSQL.
Новый случайный handoff действует ровно 60 секунд. База хранит только SHA-256 хеш.
Он содержит неизменяемый исходный субъект Core, включая integrationId и installationId.
Постоянная ссылка и пароль в этом процессе не создаются.
Повтор с новым JWT выпускает другой handoff для той же компании и того же пользователя.

Пользователь определяется external identity, затем однозначным старым `(companyId, source=amo, externalId)`.
Email не участвует в поиске или объединении пользователей.
Для нового пользователя требуется корректный email из серверного ответа amoCRM.
Отсутствующий email откатывает всю транзакцию, включая новую компанию.
Gateway возвращает HTTP 422 с кодом AMO_PROFILE_UNAVAILABLE и фиксированным текстом об обновлении профиля.
Уже связанный пользователь сохраняет профиль и входит без нового email.
Совпадение email у другого пользователя той же компании приводит к конфликту.
Одинаковый email в разных компаниях допустим.
Неактивная identity или пользователь не активируются повторным входом.

`POST /api/v1/auth/amocrm/entry-exchange` принимает только `code` и возвращает обычную AuthResponse с refresh cookie.
Неизвестный, использованный или истёкший code отклоняется до запроса Core.
Company вызывает `POST /internal/v1/company-entry/subject-check` по точному HTTPS URL из `COMPANY_ENTRY_SUBJECT_CHECK_URL`.
`COMPANY_ENTRY_SUBJECT_CHECK_KEY` содержит не менее 32 символов без пробелов и передаётся как Service credential.
Он отличается от provisioning credential и внутреннего gateway credential.
Company проверяет различие с provisioning credential, если `GATEWAY_PROVISIONING_SERVICE_TOKEN` доступен в его окружении.
При раздельных окружениях конфигурация Core и оператора обеспечивает это различие.
Отсутствующая конфигурация закрывает новый вход.
Compose передаёт только URL и callback key в company.
Core listener задаётся `COMPANY_ENTRY_HTTP_ADDRESS`; TLS перед listener завершается доверенным proxy с `COMPANY_ENTRY_TLS_PROXY=true`.
Секретные значения не передаются браузеру и не попадают в сообщения ошибок.

Сетевой запрос ограничен пятью секундами и не выполняется в SQL-транзакции.
Клиент не повторяет запрос и не следует redirect.
Core проверяет текущую исходную установку и активного, не free администратора с точным CRM ID.
Отказ Core запрещает вход. Недоступность оставляет handoff неиспользованным.
После ответа company блокирует handoff, identity, integration, user и company.
Она повторно проверяет срок, потребление, исходный субъект, provider, локальные статусы и роль.
Погашение handoff и создание session происходят одной транзакцией.
Ошибка создания session оставляет handoff пригодным для следующей попытки.
Конкурентное погашение даёт одну session. Повтор не возвращает ранее созданную session.

`RevokeAccess` теперь деактивирует только rakurs identity целевого пользователя в его компании.
Поэтому отзыв доступа запрещает уже выданный handoff и новый вход из виджета.
Выдача и повторное использование личных ссылок сотрудников сохраняют прежнее поведение.
Обычная employee session не получает административные права.
Прежние browser bootstrap и admin-self-login остаются отключёнными.

Проверка прав CRM действует на момент последнего ответа Core.
Изменение CRM после этой проверки не отзывает непрерывно действующую TeamOS session.
Для такой политики потребовалась бы отдельная непрерывная проверка session.
Потерянный ответ создания восстанавливается новым JWT и повторным входом.
Потерянный ответ погашения требует восстановления обычной session либо нового клика в виджете.
Распределённой транзакции и журнала с зашифрованными bearer нет.

Исходники REST находятся в `contracts/openapi/teamos.yaml`.
RPC находятся в `contracts/proto/company/v1/company.proto`.
Миграция `000045_amo_company_entries` и SQL запросы формируют sqlc-код.
Тесты `TestAmoCompanyEntryTransactions` используют изолированный PostgreSQL через существующий testcontainers helper.
Они проверяют реплики, разных администраторов, outbox, откаты, повтор, отзыв и обычные employee ссылки.
HTTP тесты проверяют Service credential, callback, cookies и дополнительные поля.

## Автоматическая проверка

Новые артефакты впервые запускались 10.11.2026 в отдельных рабочих копиях на Devcorps.
Работающие сервисы и данные аккаунтов не участвовали в проверке.

| Область | Среда | Результат |
| --- | --- | --- |
| Core, unit и vet | Devcorps | Пройдены для нового company-entry, CRM-клиента, API и worker |
| Core, штатные Docker format/vet/race и PostgreSQL integration | Локальный Colima, изолированный PostgreSQL 17 | Пройдены, включая реальные JWT, durable replay, миграции вверх/вниз и конфликт связи аккаунтов |
| Company и gateway, unit/race | Devcorps и локально | Пройдены для application, callback-клиента, конфигурации, gRPC, transport и auth middleware |
| Company, TestAmoCompanyEntryTransactions с race | Локальный Colima, изолированный PostgreSQL 16 | Пройдены конкуренция, разные администраторы, rollback/outbox, повтор, отзыв, несовпадение аккаунтов и истечение срока во время callback |
| Прежние employee access lifecycle и concurrent access link | Локальный Colima, изолированный PostgreSQL 16 | Пройдены |
| TeamOS frontend | Devcorps | Контракт, сборка, 37 unit-тестов и 4 Playwright-теста с реальной страницей и HTTP-фикстурами пройдены |
| Все три виджета и пакет распределения | Devcorps | Пройдены продуктовые тесты, общие настройки, сборка и проверка четырёх настоящих ZIP с тестовыми origin |

PostgreSQL-тесты на Devcorps не запускаются из-за отсутствия доступа codex к Docker socket.
Это ограничение записано в комментарии задачи ПОДК-01.01; локальные результаты не заменяют подтверждение среды Devcorps.
Проверки виджетов используют синтетический SDK и HTTP-фикстуры. Они не подтверждают установленную версию в живом аккаунте amoCRM.
Тестовые ZIP содержат зарезервированные example.invalid origin и не предназначены для установки в рабочий аккаунт.

Развёртывание новых версий сервисов и remote assets остаётся отдельной операцией.
Перед живой приёмкой требуются HTTPS ingress, реальные origin и отдельные server credentials из описанного контракта.
Фактический CRM email, OAuth установку, настройки среды и ручной сценарий проверяет пользователь.
Задачи нового сервера не входят в это изменение.
