# РС-11: ожидание, компактная очередь и настройки

Изменения ограничены локальной разработкой; применение на сервере требует миграции company 30 и совместного обновления интерфейса распределения.

## Очередь

`waitingDeadlineAt` сохраняется при первом INSERT как `createdAt + 72 hours`; миграция заполняет его для существующих строк. Повторные проверки, ручной retry и перезапуск не меняют срок. `nextShiftAt` — ближайшая известная смена по подтверждённому часовому поясу аккаунта, null означает отсутствие известной смены.

Отдельный фоновый таймер company каждые 5 секунд, независимо от CRM I/O и обработки inbox, отменяет просроченные строки без операции под SQL row lock, не перезаписывая действующую lease. Отправленные или замороженные команды сохраняют operation/idempotency identity и claims до подтверждённого освобождения guard в Core. Просрочка запрещает новое назначение в admission и validation. Отрицательный поиск Core не доказывает отсутствие эффекта: та же команда проходит expiration/tombstone после своего ValidUntil. Подтверждённый успешный результат имеет приоритет над запросом отмены; остальные терминальные результаты после дедлайна становятся `cancelled / waiting_expired`. Незавершённая сверка остаётся видимой с `waiting_expired_cancel_pending`.

В пользовательском разделе waiting находятся waiting, dispatching, uncertain; прежний assigning filter и поле сводки сохранены для старых клиентов. Сводка waiting включает все три состояния. Подтверждения считаются только после settlement. Список ограничен 15 строками, применяется offset ко всей фильтрованной выборке; порядок `(created_at DESC, id DESC)` разрешает равные timestamps. История упорядочена по уникальному sequence id и сообщает `hasMore`, не раскрывая приватные команды и CRM evidence.

## Настройки запуска

Сервер нормализует creation в pipeline + пустой status, digital_pipeline — в пустые pipeline/status. Legacy stage сохраняет старое поведение и всегда положительные CRM ID. Пустой status разрешён только для creation, оба пустых поля — только для digital_pipeline; API сохраняет прежние имена/типы полей и прежние source значения. Новая форма настроек выкладывается совместно с backend; существующие legacy правила сохраняют свои точки. DP выбирается по аутентифицированным company/binding/revision/account/group и persisted trusted trigger evidence. Текущий этап сделки сверяется с исходным pipeline/status доверенного entry: скрытие ручной точки не разрешает назначение после ухода сделки с этапа триггера. Обычный вебхук не является DP evidence.

## Часовой пояс

Core references передаёт `timezone` IANA и `timezoneFetchedAt` после чтения подключённого аккаунта. Core также передаёт проверенный домен аккаунта `accountDomain`; company строит прямую ссылку сделки по подтверждённому домену только после текущей проверки CRM permission, без дополнительного чтения каждой сделки. Неизвестный домен не подставляется. Company сохраняет последний подтверждённый результат в binding; устаревший ответ не заменяет более новый. Ручная legacy настройка не управляет расписанием. Единственное текущее подключение компании защищено `distribution_one_current_company` (миграция 22).

`GET settings` возвращает дополнительные `timezoneSource`, `timezoneStatus`, `timezoneFetchedAt`: amocrm confirmed; amocrm cached при временном сбое; legacy unavailable, если подтверждённого результата ещё нет. Браузерный/серверный UTC автоматически не подставляется. Настройки обновляют источник после 5 минут, с бюджетом 8 секунд; summary не читает CRM синхронно. Изменение timezone будит очередь и инвалидирует прежние решения, повторное подтверждение того же значения не изменяет availability revision.

## Обновление и откат

Миграция 30 расширяет queue/binding и разделяет уникальность ручной точки и DP group. Старые ключи, история и данные CRM сохраняются. До отката миграции необходимо приостановить активные DP правила с пустой точкой и восстановить прежние pipeline/status; down выдаёт явную ошибку при несоблюдении условия. Переход к старому интерфейсу требует восстановления формы точек, а не удаления очереди.

## Проверки

Company и gateway unit/race; PostgreSQL 16 integration/race: сохранение 72-часового срока после рестарта, конкурентная отмена без повторной истории, активная lease, сохранение claims у inflight, подтверждение после запроса отмены, неизвестный admission и Core tombstone, 31 запись в трёх страницах, timezone stale/outage/tenant guard, UTC/Tokyo civil-day, создание и смена режима без скрытых полей, DP group evidence и уход сделки с исходного этапа.
