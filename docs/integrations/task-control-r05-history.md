# КТ-01.R05: история, аудит и восстановление

Рабочий контракт: `contracts/openapi/teamos.yaml`. UI истории и восстановления находится вне R05.

## Чтение и страницы

`GET /api/v1/task-control/connections/{bindingId}/history` и аналогичный v2 путь возвращают
`{items, nextCursor?}`. Каждый элемент содержит `id`, десятичную строку `sequence`,
`eventType`, сохранённый `scope`, `actorId` (в v2 UUID TeamOS или `null` для автоматики),
`createdAt` и `details`. Текущие членство и `taskControl.read` проверяются при каждом
чтении. Чужой binding даёт 404. История доступна после revoke и при недоступном Core:
чтение сохранённых событий не требует свежей установки.

`cursor` — непрозрачная строка, привязанная к компании, подключению и виду списка.
`limit` по умолчанию 50, диапазон 1–100. Порядок истории — убывающий sequence,
публикаций — убывающая версия. Первая страница фиксирует верхнюю границу: новые записи
не смещают следующие страницы. Для публикаций v2 принимается также исторический
UUID cursor; новые клиенты должны передавать полученный `nextCursor` без изменений.
Смена компании, binding или типа списка инвалидирует cursor. Параметры страницы
передаются через gateway в company и проверяются там.

`GET /api/v1|v2/task-control/connections/{bindingId}/publications` возвращает immutable
публикации. Чтение требует текущего `taskControl.read`, как и история.
Одна публикация читается через `/publications/{publicationId}`. Audit не заменяет
полные снимки публикаций.

## События и diff

События: `connection_linked`, `connection_updated`, `draft_updated`, `import_applied`,
`mode_changed`, `publication_published`, `publication_restored`, `runtime_recomputed`.
Они записываются в той же транзакции, что и соответствующие изменения. API не
принимает автора и время из браузера. Автоматический пересчёт имеет `actorId: null`.

`details` содержит причину, revision/checksum и ссылки на публикации либо import.
Diff правил содержит `changedRuleCount`, `ruleChanges` с UID и видом
`added|removed|changed`, а также `diffTruncated`. В список включаются первые 100 UID;
`diffTruncated: true` явно обозначает усечение. Полный before/after для публикаций
можно получить по immutable версиям. Изменения режима/состояния/schema сохраняют
`before` и `after`. Исходные CRM captures, runtime payload, токены и assertions в
аудит не копируются.

Изменение пользовательского intent порождает событие публикации. Изменение
состава отдела, CRM-справочников или mapping может породить `runtime_recomputed`
со `sourceRevisions`, `runtimeRevision` и checksum материала. Оно не создаёт
новую публикацию intent и не приписывается последнему редактору правил.

## Восстановление

`POST /api/v1/task-control/connections/{bindingId}/rollback` принимает:

```json
{
  "expectedBindingRevision": 3,
  "expectedModeEpoch": 2,
  "requestId": "10000000-0000-4000-8000-000000000001",
  "expectedPublishedVersion": 5,
  "sourcePublicationId": "10000000-0000-4000-8000-000000000002",
  "reason": "Восстановить согласованные правила"
}
```

Результат — новая публикация с возрастающей `version` и `restoredFromId`.
Исходная публикация остаётся неизменной; draft не подменяется старой версией.
Проверяются текущие owner/admin, `taskControl.manage`, scope, fences и актуальные CRM-справочники.
Восстановление само по себе не меняет режим standalone/managed. Прежние правила, ставшие невалидными,
не применяются молча: операция возвращает конфликт/ошибки валидации.
Повторный requestId с тем же телом возвращает сохранённый результат; другое тело
конфликтует. Актуальная авторизация проверяется до идемпотентного ответа.

Для schemaVersion 2 используется v2 `/rollback`: восстанавливается прежний intent,
а динамические выборки заново разрешаются по текущим справочникам, оргструктуре и
mapping. Исторический состав отдела и старый runtime snapshot не восстанавливаются.
Новая материализация поэтому может отличаться от той, которая была у исходной
публикации. Ошибка актуального разрешения блокирует восстановление целиком.

## Хранение и миграция

Публикации и `task_control_audit_events` хранятся бессрочно; автоматической очистки
и TTL в R05 нет. Таблица аудита append-only: UPDATE/DELETE блокируются триггером.
Прикладного API удаления истории нет. Изменение политики хранения требует отдельной
административной миграции с сохранением необходимых свидетельств.

Миграция company 39 добавляет аудит и backfill существующих публикаций с их
исходными автором/временем (`details.backfilled: true`). Она не выдумывает историю
редактирования draft до миграции. Down отказывается удалять накопленные события.
Чувствительные полные снимки остаются в существующем хранилище публикаций/import,
а не дублируются в журнале.

Все management ответы используют `Cache-Control: private, no-store`.
ACK/telemetry/application-status v1 относятся к следующей задаче R07.

V1 сохраняет исходные обязательные поля `action`, `reason`, `actorId` и ссылки
`publicationId`/`requestId`. У автоматических событий `actorType: system` и нулевой
UUID `actorId`; этот UUID не обозначает пользователя. У пользовательских событий
`actorType: user`. Новые поля `eventType`, `sequence`, `details` добавлены к этому
формату. V2 использует `actorId: null` для системных событий.
