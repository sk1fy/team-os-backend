# КТ-01.R08: релизная семантика исполнения

Пакет виджета: **1.2.3**. Режимы standalone и managed используют один legacy RuleEngine; managed v2 получает actor-проекцию, уже разрешённую company. Новых бизнес-эндпоинтов для R08 не требуется: используются API R03/R11/R07. Core хранит только техническое evidence версии текущего поколения.

## Правила и задачи

| Ситуация | Результат |
|---|---|
| Пользователь отсутствует в users правила | Правило не действует |
| Изменился live actor или он неизвестен | Старый engine не применяет правила предыдущего actor |
| enabled=false либо archived=true | Правило не индексируется |
| showModal=true, denyExit=false | Список-подсказка без запрета выхода |
| showModal=false, denyExit=true | Карточный guard без списка-подсказки |
| Пересекающиеся правила | Флаги showModal/denyExit объединяются через OR после фильтрации области и checkResponsible |
| checkResponsible=true | Правило действует только при совпадении текущего пользователя с ответственным карточки |
| checkResponsible=false | Карточный guard может действовать на чужую карточку; условие проверяется по её ответственному |
| Незавершённая задача ответственному карточки | Условие guard выполнено, включая просроченную задачу |
| Задача другому сотруднику, другой карточке/типу либо завершённая | Не удовлетворяет условию guard |
| Ошибка API / неполный контекст | UNKNOWN; выход разрешён с уведомлением, отсутствие задачи не выдумывается |

Дата задачи не подменяет признак завершения: просроченная, но незавершённая задача остаётся задачей. Ответственный входит в ключ cache; при его смене используется отдельная проверка. Перед отложенным переходом выполняется свежий API-запрос. Изменения feed инвалидируют cache; DOM не является достаточным доказательством задачи конкретному ответственному.

Штатная форма amoCRM сохраняет уже выбранного исполнителя при создании и редактировании, повторном sync и смене владельца карточки. Ответственный карточки подставляется только в пустое поле. Пользователь может сохранить задачу другому сотруднику; виджет предупреждает, что она не закрывает условие для владельца. Отдельная задача владельцу создаётся только по явной кнопке с подтверждением; native submit не перехватывается для дополнительного POST.

## Принятое решение по legacy customers

Сохраняется существующее поведение, одинаковое в standalone и managed:

- список покупателей читает **первые 250 карточек на каждый набор условий запроса**; при наличии следующей страницы один раз за жизнь runtime показывает предупреждение о частичном охвате;
- в списке покупателей ищется незавершённая задача **текущему пользователю**. Флаг checkResponsible дополнительно ограничивает кандидатов карточками этого пользователя;
- карточный guard покупателей проверяет незавершённую задачу **ответственному карточки**;
- пустой customer_statuses у старого явного правила означает все customer-статусы. Выбранные статусы остаются явными;
- воронка сделок с названием «Покупатели» остаётся воронкой leads и не превращается в сущность customers.

Это осознанная совместимость, а не полный аудит покупателей. Карточки вне первой выборки проверяются карточным guard при открытии, если включён denyExit. Различие списка и guard не исправляется расширением старых правил. Отдельная helper-задача предназначена для leads; задачи покупателей создаются штатной формой amoCRM.

Список сделок показывает сделки текущего пользователя. Его существующая постраничная выборка и проверка задач продолжают работать; неполный/повреждённый ответ не выдаётся за полностью проверенный список.

## Динамические области R11

Компания пересчитывает runtime по актуальным справочникам и оргструктуре без изменения intent-публикации и черновика. Вход/выход/перенос сотрудника, его неактивность или потеря корректного mapping меняют состав соответствующей выборки. Новая открытая воронка/этап добавляется только в динамическую область allOpen; закрытые этапы исключаются.

Selected-области и legacyExplicit не расширяются на новые ID. Старые явные 142/143 не отфильтровываются новым правилом allOpen. Пересекающиеся правила остаются отдельными, не перезаписывают друг друга. При пустом составе формируется валидная пустая actor-проекция, которая выключает guard без fallback к standalone. Неизвестные/устаревшие источники не объявляются пустой выборкой; действуют проверки источников и lease R11.

Регрессионный PostgreSQL-сценарий публикует два пересекающихся intent один раз, изменяет отдел и справочники, запускает worker, читает actor bootstrap. Проверяются рост runtimeRevision, сохранность publication/draft/checksum, отсутствие чужих пользователей и отсутствие fallback при выходе/пустом отделе.

## Асинхронность и защита создания

После destroy/unbind поздний ответ не может вернуть guard, модальное окно, beforeunload или выполнить старую навигацию. Скрытие вкладки и уход на другую SPA-страницу отменяют ожидающий переход. Уничтоженный TaskChecker не запрашивает данные заново и не сохраняет поздний ответ; уничтоженный список останавливает сканирование. Двойной клик объединяется текущей операцией.

Helper создания задачи использует Web Locks с ключом account/entity и localStorage-маркер `rkrs_wt_task_write_v1:<accountId>:<entityType>:<entityId>`. Перед POST маркер записывается и перечитывается, ответственный повторно читается из CRM. Перед продолжением после каждого ожидания проверяются карточка, actor, account, владелец, применимость правил и активность вкладки.

POST задач никогда не повторяется автоматически. Timeout/abort/5xx, некорректный ответ и задержка видимости успешного POST сохраняют маркер и запрещают повторный POST после переинициализации и в другой вкладке. Само отсутствие задачи в следующем чтении не отменяет неопределённый результат. Маркер снимается, когда Tasks API подтвердил незавершённую задачу владельцу, либо при однозначном отклонении запроса (400/401/403/404/405/422/429).

Маркеры не вытесняются по TTL или при заполнении: предел 256 сохраняет защиту для неопределённых записей. Без доступного Web Locks, рабочего localStorage или accountId helper отказывается выполнять POST и предлагает штатную форму CRM. При ошибке/quota хранилища POST не выполняется.

Если задача после неопределённого результата не найдена, оператор проверяет ленту и Tasks API вручную; затем использует штатную форму CRM. Удаление конкретного localStorage-маркера допустимо только после установления результата исходной операции. Автоматического сброса маркера в этом этапе нет. Гарантия ограничена helper этого виджета, вкладками одного origin и сохранностью браузерного хранилища; она не распространяется на ручные/native/mobile/API-записи или другое устройство. Серверного CAS владельца между последним GET и POST amoCRM нет; повторное чтение сужает окно, но не создаёт транзакцию CRM.

## Проверки и поставка

- Actual AMD matrix: оба режима, флаги, responsible/users, customers, won/lost explicit, пересечение, пустая конфигурация и смена actor.
- Actual AMD execution: поздние ответы, destroy, скрытая вкладка/SPA, cache, Web Locks/маркеры, неопределённый POST, задержка Tasks API, storage/quota, owner/context changes и native edit.
- Company domain и PostgreSQL/race: динамические области, изменения источников и actor projection.
- Сквозные v1/v2/import-контракты, Node suite/syntax/ZIP, company race/lint, Core Go/vet и targeted PostgreSQL.

Core миграция 30 и backend allowlist добавляют доверенную 1.2.3 без удаления поддерживаемых 1.1.4 и 1.2.0–1.2.2. Down Core отказывает при сохранённом evidence 1.2.3. Подтверждение пакета — штатная CLI с точным generation. UI редактора TeamOS, production-миграции и живая amoCRM-приёмка в локальный прогон не входят. Браузерный контроль сохраняет границу mobile/API и не является мониторингом всех сделок.
