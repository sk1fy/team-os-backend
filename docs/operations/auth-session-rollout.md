# Refresh family rollout

Company owns validity and revocation. Gateway owns HttpOnly cookie routing. Refresh uses a 60-second one-edge replay window. A random private nonce and the presented parent derive exactly one child. The database stores only token hashes and nonce metadata. The child cannot rotate until its parent's replay deadline. Time is read after the family lock. Replay never extends that deadline or child expiry. Stale replay rejects without revoking other sessions.

All session creation and refresh operations hold a shared user lock before acquiring the family anchor. Access changes hold the exclusive user lock before locking families in ID order. Logout locks only the family and never later acquires a user lock. Token rows are mutated after the family lock. Known-ancestor logout revokes the family, including a child created by an earlier concurrent refresh. Existing JWTs retain their normal expiry.

Migration 43 is additive. It backfills historical chains by their root, including revoked ancestors, and rejects cross-account chains or cycles. Nullable family metadata permits old SQL inserts during the expansion stage. New code adopts any remaining legacy chain under its root-family anchor. Already-rotated legacy random tokens cannot reproduce their random successors. They reject without revocation; current legacy tokens still work.

Apply the migration first. Before starting the new auth implementation, drain all old company writers and gateway instances, including their in-flight requests. Start the compatible company and gateway versions together after the drain. This change is not safe as a mixed-writer rolling activation. An old writer can still revoke an entire account on retry. Additive columns do not change its behavior. No automatic deployment or activation is included here.

Rollback after activation requires retaining the new family-aware reader and revocation protocol. Do not roll back directly to the original auth binaries. Schema downgrade requires stopping all auth writers. Take a database backup before any operational downgrade.

Explicit login, registration, invitation acceptance, access-link exchange, impersonation and widget completion select a new family. Bootstrap paths that return an access link select the family when that link is exchanged. Gateway sets `teamos_session` plus `teamos_refresh_<UUID>`, and expires the legacy fixed cookie. The nonsecret selector has a fixed 365-day routing lifetime, independent of the sliding 30-day secret lifetime. Refresh never extends or writes the selector. A sufficiently long-lived login may need explicit login when its selector expires.

Refresh and logout use a captured `X-Teamos-Session` UUID or `legacy` routing marker when provided. This is not authorization; company validates token/family consistency before mutation. Without that header, selector presence forbids fallback even when malformed, unknown, revoked or missing its token cookie. An explicit captured legacy operation can still target only the legacy cookie after another login. The frontend coordinator must reject its stale JSON by epoch. Refresh never selects a family. Successful logout expires only the captured operation's cookie and never clears the selector. Failed logout and all failed refreshes leave cookies untouched.

The REST response's optional `sessionId` is the family UUID in selected mode and `legacy` in legacy transport mode. Legacy refresh stays fixed-cookie until explicit session creation. All credential responses have `Cache-Control: private, no-store`. Pending logout retains its captured routing context across reload and retry. Cookie routing cannot serialize concurrent explicit logins; the frontend must hold its shared mutation lock through full response consumption.

The same-family delayed response recovery horizon is 60 seconds, not arbitrary response delay. A much older response can require sign-in again. It cannot replace the selector of a newer family or revoke unrelated families. Token pruning retains replay rows through their deadline and clears historical FK links on deletion. Logout of an already-pruned ancient token is an idempotent no-op. The normal logout race is covered while its predecessor is retained.
