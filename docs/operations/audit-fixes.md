# Подготовить исправления аудита к выпуску

Исправления затрагивают backend и frontend TeamOS. Выпускайте совместимые версии обоих репозиториев.

1. Подготовьте два разных случайных служебных секрета длиной не менее 32 символов.
   `TASKS_COMPANY_SERVICE_TOKEN` связывает Tasks с Company для разрешения должности в пользователей при повторении задач.
   `ACADEMY_FILES_SERVICE_TOKEN` связывает Academy с Files для фонового копирования файлов.
   Production Compose требует оба значения и не принимает development-значения в проверке конфигурации.
2. При запуске сервисов вне Compose задайте соответствующие пары переменных.
   Company получает `COMPANY_TASKS_SERVICE_TOKEN`, Tasks получает `TASKS_COMPANY_SERVICE_TOKEN`.
   Files получает `FILES_ACADEMY_SERVICE_TOKEN`, Academy получает `ACADEMY_FILES_SERVICE_TOKEN`.
   Значения внутри каждой пары должны совпадать. Для Tasks также нужен `TASKS_COMPANY_GRPC_ADDR`.
   Старый `FILES_TRUSTED_METADATA` больше не разрешает доступ по неподписанным заголовкам.
3. Проверьте `GATEWAY_TRUSTED_PROXY_CIDRS` по реальной схеме reverse proxy.
   Не добавляйте недоверенные сети. Без этой настройки лимитер считает IP непосредственного соединения.
   Refresh имеет отдельный бюджет 600 запросов в минуту на IP. `/auth/me` не расходует бюджет входа.
4. Выполните `make check-production-compose` и `make check-contract`.
5. Примените миграции Company 43 и 44 через существующий механизм миграций.
   Миграция 43 добавляет семейства refresh-сессий. Миграция 44 добавляет порядок outbox.
   Соблюдайте обязательную остановку старых auth-writer по [инструкции обновления сессий](auth-session-rollout.md).
   Смешанная работа старого и нового протокола refresh небезопасна.

Эта инструкция не запускает выпуск. Production-данные и процессы автоматически не изменяются.

Для локальной проверки используйте `make test-race` и интеграционные тесты изменённых сервисов с `GOWORK=off`.
PostgreSQL-тесты используют testcontainers и требуют работающий Docker.
Во frontend выполните `npm test`, `npm run build` и `npm run e2e:auth`.

Получателей назначения на должность Tasks фиксирует через RPC Company во время команды, до записи outbox.
Отказ Company не превращается в пустой список и не сохраняет изменение задачи.
Доставка события не пересчитывает получателей по текущему составу должности.

Исторические уведомления, потерянные до исправления, автоматически не восстанавливаются.
Не удаляйте `processed_events` для слепого повтора. Для восстановления нужны исторические назначения и отдельная проверяемая процедура.
Необработанные старые события только с должностью отклоняются и проходят существующую политику повторов и DLQ.

Снимки KB, выданные для копирования в курс, сохраняют идентификатор и метаданные версии.
Удаление статьи, на которую ссылается такой снимок, возвращает 409. Снимите статью с публикации вместо удаления.
Черновики больше не попадают в события обновления содержимого Academy.

Публикация JetStream, включая DLQ, ограничена пятью секундами.
При неизвестном результате сохраняется прежний идентификатор события для повтора.
Company не пропускает позднее committed-событие мимо раннего неопубликованного события той же компании.
Это более строгая очередь для committed-строк, чем отдельные очереди агрегатов.

Повтор refresh восстанавливает тот же токен в течение 60 секунд после ротации и не продлевает это окно.
После окна старый токен отклоняется без отзыва других сессий.
Существующие access JWT после logout сохраняют обычный срок действия.
